# FitAgent 领域型长期教练架构设计

日期：2026-09-30。状态：设计提案，待确认后分阶段实施。本文不表示重构已完成。第二轮细化见第16—21节；与早期概述冲突时，以细化契约为准。

## 1. 核心决策

FitAgent（健身教练智能体项目）的目标不是复制编程助手，而是对用户明确委托的健身任务持续负责：理解请求、读取可靠证据、提出有依据的方案、遵守日期与运动约束、按授权执行、核验持久状态、随后检查是否真正落实及是否有帮助。

选择“领域状态为中心、模型参与决策、统一受控执行、长期责任驱动”的架构。保留不同认知策略，但不保留多套权限与副作用边界。短对话、明确业务操作、后台复盘均使用同一个 Harness（执行控制层，管理上下文、权限、工具、预算、状态和审计）。

第一轮不引入新的任务框架，不把所有请求强行改为模型自主循环，不重写已经存在的记忆系统，不立即增加多个独立智能体。复用现有服务、队列与业务模型；新的逻辑契约不等于立即增加数据库表。

### 已确认的边界冲突

1. `coach_agent.py` 的打卡入口满足规则后直接调用计划调整；新责任为调整需询问。二者需要统一账户级动作政策，不能只限制后台责任入口。
2. 新调整执行复核责任、期限、完整计划快照，但该段未复核最新目标、偏好及风险证据。草案依据可能在等待期间过期。减组本身也不能被包装成完整安全决策。
3. 自动生成长期任务只证明系统在跟踪，不证明用户委托了主动运行。跟踪状态、责任与授权必须分离。
4. 旧架构文档含“更聪明”、估计耗时和全面替换路线等早期表述，与当前混合实现不是同一状态。后续以本文的目标设计和责任实施记录的事实为准，保留旧文用于历史理解。

### 需要补充验收，而不是直接断言没有实现

全部写入口的幂等覆盖；目标更新到排队任务的失效传播；多进程工作者抢占；外部副作用后的状态核对；完整输入的实际分词预算；风险词表及否定/历史症状处理；全前端真实鉴权接入。这些必须通过逐路径清单和固定案例核实，不能从局部搜索得出“全系统已完成/完全没有”。

## 4. 目标结构

```text
用户消息 / 结构化操作 / 已提交业务事件 / 到期扫描
                         ↓
             入口归一：身份、请求号、来源、时间
                         ↓
           单次执行上下文与任务契约（按版本冻结）
                         ↓
       语义候选 → 多任务拆解 → 风险与动作政策
                         ↓
       证据读取 → 分析/知识/教练能力按需调用
                         ↓
           有限规划循环或确定性短流程
                         ↓
       只读回答 / 澄清 / 草案 / 等待明确批准
                         ↓
           执行前复核 → 业务工具 → 提交与回查
                         ↓
            公共事件、用户可见结果、效果评估
                         ↓
            有依据的经验记忆；后续到期再唤醒
```

所有认知路线共享底部执行边界。入口与后台任务不得绕过身份、授权、风险复核和业务校验。模型不可直接写数据库，也不能通过“最终回复”宣称尚未提交的动作已完成。

## 5. 状态所有权

| 对象 | 回答什么问题 | 权威位置及演进 |
| --- | --- | --- |
| 目标 | 用户想达到什么，期限/指标/边界是什么 | 第一阶段通过统一读写入口继续使用已确认档案目标；现有目标表在本次应用代码搜索中仅见定义，不能因为表存在就直接迁移权威。结构化目标及多目标关系另行审查数据用途后决定 |
| 当前状态 | 体重、实际训练、恢复、当前偏好是什么 | 业务记录和已确认档案；保留来源、发生时间、记录时间及纠正关系 |
| 计划 | 接下来哪天做哪种训练 | 已确认计划；日期、类型、时长、器械、禁止动作作为结构化硬约束 |
| 跟踪状态 | 系统跨回合关注哪个问题 | 现有长期任务；允许从业务派生，但无调度或写权限 |
| 责任 | 用户让系统持续做什么、到何时结束 | 现有长期任务中的显式责任配置；指向目标而非复制目标，记录触发和权限范围 |
| 一次执行 | 本次做什么、处于什么状态 | 现有运行记录；后台时关联队列任务，不将目标、责任、任务、运行混用 |
| 审批 | 这一次具体变化是否允许 | 持久审批绑定用户、资源、版本、参数、依据、期限；批准不表示已执行 |
| 效果评估 | 动作落实了吗、观察到什么变化 | 现有决策与效果评估，不由回答语气或任务完成状态推断 |
| 长期记忆 | 过去发生什么、何种经验适用 | 现有事实/经验/归纳系统；只提供证据背景，不覆盖当前目标/计划/权限 |

同一用户允许多个目标，但第一版必须明确主要目标及每项责任关联哪个目标。目标达成、计划完成、责任到期是三个不同状态。用户改目标后，不自动修改历史训练记录，不删除旧记忆，不默认接管新的长期责任。

## 6. 模型、领域能力和工具

### 6.1 模型承担什么

理解复杂表达，抽取多任务和槽位，提出澄清，选择可用只读工具，解释已计算的证据，提出调整候选，生成自然教练沟通。小模型、规则和较强模型可替换比较，但输出统一候选契约。

模型不承担身份证明、写权限最终裁决、时间计算、数值统计真值、事务提交、批准消耗和结果核对。明确请求若缺必需槽位先澄清，不能用历史偏好补成用户本轮明确授权。

### 6.2 三类能力，不先做三个自治智能体

- 数据分析能力：训练完成率、记录覆盖率、恢复评分分布、计划执行差异；由已注册计算工具输出数值与来源。区分未记录和零训练，不对缺失值填零。
- 领域知识能力：检索受控健身知识，记录来源及适用范围；不可信检索文本仅作数据，不能变成指令。领域安全策略仍由宿主强制执行。
- 教练能力：用目标与现实限制解释选择，支持用户协商、拒绝和修改；信息充分时直接给可行动建议，避免机械连问。

现有工具要逐项标记“内部处理阶段”还是“模型可调用业务能力”。例如档案抽取与写记忆不应默认开放成可随意调用的用户动作。

目标业务工具包括：读取档案/计划/证据、查询有效记忆、计算训练与恢复摘要、读取知识、生成计划草案、验证约束、提交获准计划变化、提交训练记录及其纠正、创建或更新明确责任、读取执行结果、提交回访答案。名称和参数先登记在契约表，不要求现在新建全部工具。

每个工具必须声明：用户/资源范围、输入输出、只读或写入、授权依据、版本前置条件、是否可重试、写后验证与失败核对方式。只读也需要访问控制。用户明确要求记录一条完整训练时可以按明确请求执行，不必对所有低风险写入额外弹审批；系统主动调整必须按委托政策询问。

## 7. 统一单次执行控制

每次执行携带用户与会话/责任关联、原始请求号、触发来源、目标/计划/档案/风险依赖版本、硬约束、权限、输入证据、预算及可核查事件。

固定控制顺序：身份与资源范围 → 语义/任务 → 读取必要当前风险与状态 → 风险和动作政策 → 缺槽澄清 → 按需补充证据 → 计划候选 → 校验 → 获准 → 最新依赖复核 → 执行 → 提交 → 状态回查 → 回复。风险门禁不能仅凭语义候选运行；需要读取当前证据。

简单问答可以只执行必要只读步骤；确定性控制步骤不得由模型选择跳过。计划失败可以在预算内修复候选，但修复不能扩大授权或偷偷移除用户约束。规则回退必须显示真实来源，不能伪装成模型决策。

状态至少区分：准备、运行、等待用户、等待审批、完成、失败、取消、依赖失效、结果未知。过程事件的校验完成不等于事务已提交；用户界面只有获得提交/回查证据才显示已修改。

第一版预算提案：一次模型工具循环最多6步，计划候选最多修复1次；总时间和输入/输出预算由配置确定，先测延迟再锁值。预算不足保留状态并解释未完成项，不能为赶回复绕过校验。过去文档中的估计延迟不是验收结果。

## 8. 纠正传播：不止防止旧记忆检索

用户：“下周只跑步，不做力量，周三改到周五。”

1. 抽取变更范围与生效区间；“下周”按用户时区锚定，不把周偏好改成永久偏好。
2. 对缺歧义的明确约束提交新版本；存在冲突时先澄清。
3. 复用旧事实失效机制，刷新现有目录/摘要/记忆块；审计仍能查看历史。
4. 失效依赖这些约束的旧候选、审批与未执行任务。已发生的训练保留历史事实。
5. 旧效果评估保留原基线，标记目标变化/干预变化，不能将之后的变化归因于旧方案。
6. 下一次规划和执行读取最新状态，再核对版本；队列内保存的旧上下文不是权威。

实现前需建立依赖清单。第一版先用业务版本/标识及必要字段快照校验，不增加无意义哈希。版本变化采取保守失效，可能拒绝仍然有效的草案，但不会默默执行过时方案。用户自述某症状已解除不等于自动证明任何训练都安全。

## 9. 长期闭环与通知

明确委托 → 责任到期或相关事件 → 更新证据 → 必要时生成分析 → 提案或回访 → 获准执行 → 观察实施与效果 → 写入受条件限制的经验。

训练/打卡事件在提交后更新证据与评估状态，不每条触发模型。固定到期与事件触发合并到同一责任时段，设置冷却，避免旧回访和新周复盘重复提问。

第一版保留站内活动，不默认为外部推送。通知政策另存用户选择：时区、安静时段、频率上限、同问题合并、停止提醒。责任到期停止新动作，但已执行动作的效果观察可按原约定继续；这不能成为继续调整计划的授权。

安全异常时暂停相关提案并展示边界内的提示/必要澄清；不声称紧急监护、诊断或替代专业医疗判断。无记录只报告证据不足；不能将没有症状记录等同于确认无症状。

## 10. 数据与效果：领域内最容易遗忘的部分

- 输入规范：单位、用户当地日期、发生时间/提交时间、来源、是否完整、纠正版本；只有日期的记录保留粒度，不伪装精确到小时。
- 目标指标：目标期限、可测指标与用户可接受约束，避免仅保存“减脂/增肌”标签。
- 实施状态：计划已保存、用户已查看、用户明确说做了、日志支持做了，分开记录。改完数据库不代表训练落实。
- 观察结果：执行率、疲劳变化等属于观察，合成评分阈值不证明健身收益或因果效果。
- 变化归因：基线、观察窗口、计划版本、用户是否落实、证据缺失和同期目标变化；不足时不产出强结论。
- 知识与风险：保留证据来源及适用范围；旧症状、引用、否定与当前症状分开。策略记忆不得跨用户共享个人资料。
- 隐私与生命周期：按用户授权保留/导出/撤回；设计删除流程不等于授权删除本地数据，本轮不执行任何删除。

## 11. 并发和恢复边界

以用户+资源为冲突范围，不用全局锁串行所有用户。请求登记、资源版本检查、审批消耗和本地业务修改应满足事务边界；两个不同会话同时修改同一计划，最多一个基线可成功，另一个明确失效。

数据库内操作可使用同事务保证一致性，但不声称网络与外部服务恰好一次。外部动作要有请求标识与查询核对能力；响应丢失后进入 outcome_unknown（结果未知，可能已经发生副作用），先查后决定，不盲目重发。

后台任务需要抢占令牌、租约/心跳及过期处理设计：只读任务可按策略重跑；写任务先核对提交、审批与目标资源。扫描和队列公平性、用户配额、模型调用并发及成本上限是部署验收项。当前 SQLite（轻量数据库）的隔离测试不能证明 PostgreSQL（生产关系数据库）的多工作者行为。

## 12. 前端：展示业务闭环而不是模拟思考

保留现有聊天、计划、日志、恢复和长期跟踪页面，不新造一个替代应用。

- 聊天：回答与必要澄清；草案卡展示具体日期、类型、变化、依据和权限。公共过程默认折叠。
- 计划：已确认版本与待批准变化分离；不能将草案渲染成当前正式计划。
- 长期跟踪：目标/责任/一次运行分层显示；下一次触发、缺什么证据、是否要用户处理。
- 活动：审批、结果未知、回访及执行结果集中展示，和聊天引用同一对象。
- 过程：展示读取、计算摘要、模型公开决策摘要、校验、审批、工具与回查的真实状态；没有发生的步骤不补造。

当前独立演示入口用于无数据库交互演示，不等于真实登录业务链路。设计后的用户验收必须进入实际认证壳和真实接口，不能只看演示截图。

## 13. 分阶段迁移与门禁

### 阶段一：统一政策与依赖契约

逐项登记所有写入口，优先打卡自动调整、聊天计划调整与后台审批；明确目标权威与档案投影，确认临时/永久约束。先不替换模型或框架。

验收：同一用户的“调整先问我”对三个入口一致生效；明确训练记录仍可保存；后台不得从自动跟踪状态获取写权限；目标/风险改变使相关旧草案失效。

### 阶段二：收敛单次执行控制

已有短流程、模型规划与后台执行共用动作政策、证据依赖、预算、公共状态及回查。先迁移一个计划调整及一个记录纠正场景；避免一次重写全部教练服务。

验收：三种入口都可从最终业务状态与事件轨迹核验；响应丢失不重复写；自然语言理解不稳定时停在澄清而非错误行动。

### 阶段三：接回效果闭环

把新责任调整关联已有决策与效果评估；保留既有打卡/训练事件和回访，统一到期合并。

验收：没有落实不能记成策略失败；缺证据不宣称改善；纠正记录后重新评估或明确旧结论失效；责任到期不等于目标成功。

### 阶段四：模型与领域体验对照

固定协议后比较规则短流程、现有模型规划、统一执行控制下的模型策略；再判断是否需要独立分析/知识/教练子智能体或意图再训练。框架升级必须有收益证据。

验收：报告任务成功、约束遵守、过时事实误用、授权违规、工具调用、预算与延迟；模型原始错误与宿主拦截分开统计。

### 阶段五：实际部署与真实界面

单独审批数据库迁移，核对工作者启动、生产数据库并发、恢复、权限隔离和前端鉴权。合成数据仍用于压力及故障验证，不冒充真实健身收益。

## 14. 固定验收场景草案

先冻结场景语义与最终状态，再编写数据；开发/校准与最终未参与调参的测试分开。用户身份、目标、计划、证据和时钟采用隔离构造。长实验留可读日志及逐例结果，失败案例不删除。

1. 周五仅慢跑：其他日期和类型不被偷偷替换。
2. 只询问、引用他人或否定请求：不创建计划/责任。
3. 一条消息记录训练并禁止推举：保存许可记录，拦截被禁止动作。
4. 先生成草案，后改目标：旧审批/队列失效，历史记录仍可审计。
5. 等待批准期间新增风险证据：不执行旧草案，不用减组替代风险处理。
6. 明确委托调整先询问，再提交高疲劳打卡：打卡不绕过询问。
7. 同日纠正睡眠或疲劳：旧事实和派生摘要不进入执行上下文。
8. 明确清空字段与未提交字段：分别清空与保留。
9. 已批准但工作者未运行：界面不显示计划已改。
10. 写后响应丢失：结果未知/回查，不重复动作。
11. 两会话同时改计划：只允许一个基线提交，另一个可解释地失效。
12. 责任暂停/取消/到期：队列不继续写；效果观察按明确约定处理。
13. 没有训练日志：未知而非零训练，不编造策略收益。
14. 训练有记录但未证明采用建议：不强行归因。
15. 用户拒绝后续追问：不继续重复催促。
16. 用户时区、午夜和夏令时：窗口与日期一致，无重复唤醒。
17. 不可信记忆/检索文本要求扩大权限：仅作数据，不执行注入指令。
18. 跨用户对象编号：读取、审批、执行和过程日志均拒绝越权。

权限越界、跨用户泄漏、重复不可逆写入、过时批准仍执行等属于零容忍工程门禁；小型固定测试中零失败不等于真实部署零风险。模型质量、延迟和成本目标先测基线再确定，不预写提高百分比。

## 15. 本轮交付与边界

本轮只新增本文：阅读已有设计及相关代码，检索官方领域资料，归纳目标方案和迁移门禁。未改运行代码、依赖、配置或数据库；未启动服务、工作者、模型训练；未重跑历史测试。因此本文提供的是设计与审计结论，不是新的功能完成或效果证明。

后续第一项实施应为“统一动作政策与执行依赖”，而不是先做更漂亮的思考展示、重新训练意图模型，或者接入新框架。

## 16. 第二轮优化：缩小首轮范围与修正假设

本轮继续设计，不实现运行代码。新增核对发现：

- `FitnessGoal` 在本次应用代码范围搜索中仅出现于模型定义，不能证明实际数据库为空，也不能证明所有外部调用没有使用。撤回立即将其指定为权威目标的决定。
- `CoachAgentService.adjust_plan`（现有教练服务的整周计划调整方法）归档有效计划并调用构建器重建七天计划，不是新责任切片的指定日期减组。两个行为必须拆开命名、权限、预览和验证。
- `ApprovalManager.requires_approval`（现有审批需求判断方法）按副作用/写权限要求批准；新设计允许范围充分明确的用户记录直接执行。这是待迁移的政策变化，不能宣称已经一致。
- `ToolRegistry.execute_awaiting_approval`（带审批入口的工具执行方法）在未提供审批管理器时可直接走执行。不能用“所有调用者都应自觉传参数”作为统一边界；第一轮需审计并收拢可达调用路径。

首轮仅支持：训练记录及纠正、指定日期计划局部变更、有限期周复盘。整周替换仍可保留为明确用户操作，但不把它作为疲劳事件的默认动作。饮食、多模态、外部可穿戴、独立子智能体不在这轮扩张范围。

目标维护先统一业务访问入口，继续使用当前档案确认值。结构化目标、版本字段存放和数据库约束后续给出独立变更清单，再获准实施。不能用新的设计覆盖旧数据库中的未知用途。

## 17. 动作政策：按实际变化判断，而不是按工具名字判断

### 17.1 政策输入与裁决

裁决输入包含：已认证用户、入口来源、动作类别、具体变化、目标资源、当前请求证据、范围/生效区间、长期委托范围、账户限制、当前安全证据及必要槽位。

裁决只有五类：允许只读、允许本次明确动作、要求澄清、要求批准具体草案、禁止。必须附可核对原因和所用政策版本。模型置信度、过去批准次数、记忆归纳和后台任务存在都不能作为写授权。

拒绝条件优先：越权、禁止动作、失效依赖、安全禁令不能被本次确认覆盖。账户与责任范围取交集；责任不能放宽账户限制。用户明确批准一个具体变化可满足“先询问”，但不永久改写账户政策。用户想修改长期权限时必须走独立、明确的政策变更流程。

| 动作与情形 | 首轮裁决 | 必须验证 |
| --- | --- | --- |
| 查询自己的计划或历史 | 允许只读 | 对象归属与实际读取范围 |
| 明确要求记录已完成训练，必要信息齐全 | 允许本次明确动作 | 事实/假设区分、单位、时间、重复请求 |
| 明确纠正唯一可定位记录 | 允许本次明确动作 | 旧记录版本；对象不唯一则澄清 |
| “改一改计划”或“以后帮我安排” | 要求澄清或预览 | 不能自行补出整周替换范围 |
| 后台依据疲劳建议减组 | 要求批准具体草案 | 指定日期、动作变化、依据、依赖、有效期 |
| 用户已看到完整局部变化并明确批准 | 允许本次明确动作 | 消耗一次批准，执行前重新复核 |
| 重建并替换整周计划 | 明确整周替换预览后批准 | 被移除/新增日期与运动、历史计划保留 |
| 删除、扩大授权或临床诊疗动作 | 首轮禁止或不支持 | 不通过提示词或一般批准绕过 |

### 17.2 入口一致性与失败保守

聊天、结构化接口、打卡派生调整、后台工作者都向同一政策服务请求裁决；缺失执行身份/裁决凭证时，业务写处理器拒绝。内部日志、运行状态等必要运行记录不与用户计划写授权混同，但同样必须受用户归属和事务约束。

裁决凭证仅在宿主内部创建，绑定请求、动作参数和资源。不可接受模型或客户端自带的“已授权=true”。底层工具处理器必须检查凭证并回读依赖，不能只依靠前端禁用按钮。

兼容期保留旧代码但显式封住未迁移写路径；普通只读回答不受影响。不能用未通过新入口的旧执行方式作为失败回退，否则统一权限形同虚设。

## 18. 依赖、纠正与并发的实施契约

### 18.1 最小任务契约

每项候选动作记录：用户、请求/事件标识、触发来源、动作与资源、发生/生效时间、用户原话证据、硬约束、基线、候选变化、依赖清单、政策裁决、批准标识及截止时间、执行与核验状态。

依赖分两类：硬依赖变化使动作失效；辅助背景变化只影响解释。硬依赖至少包含目标语义、相关时段约束、运动禁令/风险状态、计划版本、责任有效性和政策。用户无关的聊天标题变化不使草案失效。最早版本可使用相关字段快照与既有标识，不新增哈希；后续才评估单调版本字段。

| 变化 | 局部调整候选 | 已执行的历史 | 效果评估 |
| --- | --- | --- | --- |
| 目标或目标期限变化 | 失效，要求重新规划 | 保留旧目标关联 | 保留基线并标记目标变化 |
| 相关日期/运动约束纠正 | 失效，不直接修改旧批准参数 | 保留真实发生记录 | 标记干预变化，必要时终止旧窗口 |
| 当前风险新增或相关风险解除 | 重新安全判断；不得直接沿用旧批准 | 保留证据历史 | 区分安全提示与效果归因 |
| 相关训练/恢复记录被纠正 | 失效并重算证据 | 标记记录的新旧关系 | 旧结论标记待重算，而非悄悄覆盖 |
| 无关时段的辅助备注变化 | 不必失效 | 保留 | 仅在确实影响分析时更新 |
| 执行日期已过去或批准已过期 | 失效，不偷偷顺延到下一天 | 保留已发生动作 | 不伪造实施结果 |

“撤销刚才的操作”也必须区分：尚未执行可取消；已提交则需要新的纠正/补偿动作及其授权。不能删除审计来假装动作没发生。

### 18.2 不能只靠执行前读一次版本

存在检查与提交间隙：工作者读到旧目标，另一个会话提交纠正，工作者再保存旧草案。设计要求有关联状态更新和计划写入遵守同一短事务并发边界，固定加锁顺序或采用真正的数据库条件更新；所有相关写入口都参加，不能仅锁计划行。

模型推理、检索和用户等待放在事务外，不持锁等待网络。提交前短事务重读依赖、重新裁决、消耗批准、更新目标资源、登记结果；同事务失败全部回滚。若条件不满足结束为依赖失效，不自动以新状态重写获批草案。

资源加锁/条件更新实现将在生产数据库专项验证后选择；本文没有为现有数据库新增字段或加锁代码。轻量数据库单进程测试不能证明上述竞争窗口被解决。

### 18.3 传播一致性

权威纠正与旧草案失效/待重算标记应在同一事务提交；昂贵摘要更新可异步进行，但默认检索必须先过滤失效事实。摘要仍旧时明确使用直接事实或重新构建，不能继续把旧摘要当作有效信息。

后续事件通知可延迟，不影响执行前权威复核；需设计已提交事件登记及幂等消费，不用“内存回调肯定能运行”保证一致性。第一轮优先复用现有任务与事件持久记录；是否需要新增事件投递结构另行审查。

## 19. 多任务与长期效果的遗漏补齐

### 19.1 一句话有多个动作

将任务拆成有依赖顺序的动作：纠正档案→读取新档案→生成候选，或者独立的训练记录+只读解释。后续动作必须消费同轮已确认更新，不允许全部使用回合开始的旧快照。

独立动作允许部分完成，逐项显示“已保存/等待澄清/等待批准/失败”；一个动作成功不意味着整轮成功。存在整体业务一致性要求时才合并短事务。已提交动作不因后续模型失败而重复执行；最终回复缺失也不能触发重放全部任务。

### 19.2 效果链不能把计划提交当成训练落实

计划修改提交成功后，登记实际变化对应的决策和评估关联；候选被拒绝/过期不创建“已实施干预”的效果记录。仍需独立观察用户是否采用修改后计划。

记录只支持“用户自述落实”或“日志支持落实”等证据等级，不宣称证明用户实际训练。结果不足分别显示：尚未观察、未落实、落实不明确、证据不足、观察改善/变差；不能合并成策略失败。

对相关源记录的纠正使已形成的结论标记待重算，同时使由该结论产生的经验在当前执行视角不可用，复用既有记忆关系。保留历史结论及修订理由，不悄悄更新原结论的文字并继续引用旧置信度。

跨用户泛化或自动训练不包含在本轮闭环：一个人的经验只在相似目标、阶段与状态下作为参考；观察性数据不能证明动作因果有效，合成数据只能验证系统行为。

## 20. 从设计收口到首个实施切片

首个切片：用户明确“计划调整先问我”→高疲劳打卡→只保存打卡和调整草案→用户纠正约束→旧草案失效；另一个分支用户不改约束而批准→只改变指定日期→登记效果观察。

这个切片复用已有前端和审批，重点不是新增展示。核心预期：记录保存一次；批准前计划零变化；获批后差异严格等于预览；纠正后旧任务零写入；页面与聊天显示同一持久结果。

实施前要交付并冻结：

1. 写入口清单及真实动作范围，包含结构化接口和打卡派生调用。
2. 政策裁决输入输出、范围/生效期与原因。
3. 候选依赖及当前存放位置；若需迁移，单独说明影响。
4. 并发与事务策略、失败后的只读核对步骤。
5. 固定场景初始状态、预期终态、禁止差异与日志口径。

建议新增六类对抗场景：批准后但写前纠正、同轮先纠正再规划、已批准但执行日已过、相关原始数据纠正后旧经验不可用、一次多任务部分完成后重载、旧整周调整回退不得绕过局部审批。

## 23. 自由模型循环能力收口（2026-10-01）

## 24. 受控业务验证来源绑定（2026-10-01）

记忆写入与计划修复在写处理器调用前核对当前注册表的宿主成功验证记录。记录不来自模型参数，深拷贝隔离、一次消费；重新验证失败撤销旧记录，经过模式修复的结果不产生写入凭据。记忆抽取必须一致，允许主动缩小已通过候选；计划修复绑定原验证输入、上下文与输出，并核对当前用户画像、目标归属、有效状态及重读计划内容。拒绝发生在业务写处理器之前，记为blocked、零执行，而不是写结果未知。

这是流程内来源约束，不是加密签名或跨进程锁。验证结果本身的语义质量仍依赖现有验证器；受信内部辅助函数与其他业务生产者尚未统一迁移。当前计划重读与保存之间仍存在并发窗口，后续需要生产数据库上的原子版本比较及共同写入协议。阶段测试与可复现命令见[来源绑定实施日志](../logs/experiments/20261001_verified_write_provenance.md)。

## 25. 共享计划写入边界（2026-10-02）

两个计划内容更新入口（修复、审批指定日调整）统一采用数据库条件更新：当前用户、目标、active状态与完整旧内容同时匹配才写入。生成与整周替换在读取当前计划前取得同一用户行锁，已有审批流程采用相同用户锁顺序。内容冲突确定没有业务写入时记为blocked，不自动重试；审批失效，不生成成功决策。原事务负责计划、审批和决策的提交或回滚。

不新增字段、迁移或哈希。PostgreSQL使用现有JSONB内容比较；SQLite序列化键顺序可能保守拒绝等价内容。用户行锁只约束遵守共同协议的生产者，SQLite不具备相同行锁语义；不能据此声称整体领域状态或生产并发已经验收。来源绑定仍校验上下文及画像，但其他生产者的跨进程依赖协议尚未全部统一。实施证据见[日志](../logs/experiments/20261002_shared_plan_writes.md)，统一进度见[重构状态](FITAGENT_REFACTOR_STATUS.md)。
