# 个人智能体闭环审计与验收方案

日期：2026-10-04。范围：静态调用检查及既有离线测试，不修改运行架构，不进行付费模型调用。

## 已核对的边界

- `decision_evaluation.py` 的 `_implementation_status` 对训练计划和饮食建议，优先采用明确随访回答；缺少回答保持 `unknown`。后续有活动记录，不代表采纳了这次建议。
- 正式评估完成路径向结果反思服务传递评估计划中的执行状态，而不是固定写成已执行。
- `outcome_reflection_service.py` 的批量入口 `reflect_recent_decision_outcomes` 固定传入 `implemented`。这是需要收敛的旧入口，不应绕开正式评估计划获取执行证据。
- 本次全文检索在 `fast_api` 和 `tests` 内发现该批量入口的服务包装和记忆测试调用，没有发现直接业务调用；这不是动态运行未被调用的证明。
- 周期责任的 `review_delivery: persisted_review_result` 表示复盘交付成功，不表示用户目标改善。应保留交付指标，并与建议采纳、实施证据、观察结果分别呈现。
- 现有固定旅程测试声明使用合成案例并禁止作为训练材料；其离线通过不能替代真实模型验收。

## 已执行的最小修补

1. 批量入口不再传入固定的已实施状态：只查询同账号的既有正式评估计划，调用其刷新流程。缺少计划直接跳过，不自动补造采纳证明。
2. 复用正式流程中的实施确认、最小证据量、观察窗口、安全检查、依赖失效及重复结果检查。旧调用参数 `outcome_window_days` 保留兼容，但不覆盖评估计划的正式观察窗口。
3. 补充有记录但未确认、无回答、明确未开始或放弃、部分实施、缺少计划、证据不足和结果重复运行的批量入口回归；依赖失效沿用正式评估的已有测试。
3. 不新建结果数据库或重复的记忆系统，复用现有评估计划、随访、结果和记忆依赖。

## 连续旅程验收协议

复用现有业务回放与固定旅程设施，不再增加一套重复框架。

| 阶段 | 输入或事件 | 必须观察到的业务结果 |
| --- | --- | --- |
| 建立安排 | 用户明确指定训练日、运动类型和复盘权限 | 日期与类型进入约束；未授予的写权限不得推断 |
| 部分执行 | 用户上传部分训练和恢复记录 | 区分已记录、未知及明确未完成，不补造缺失数据 |
| 环境变化 | 用户临时出差并纠正旧记录 | 旧证据失效传播；当前计划版本成为唯一写入依据 |
| 多领域复盘 | 训练、饮食、恢复子任务读取有效上下文 | 每份建议附证据和不确定项；冲突由主流程处理，不互相覆盖 |
| 待审批变化 | 等待审批时用户再次修改计划 | 旧草案不能错误覆盖新版本；必要时重新生成草案 |
| 用户回应 | 批准、拒绝、暂停或不回复 | 批准才执行；拒绝不反复追问；暂停停止相应责任；沉默不视为同意 |
| 后续观察 | 用户说明采纳情况并提供后续记录 | 建议、采纳、实施、结果分别记录；观察关联不等于因果效果 |

## 真实模型阶段的条件

- 先完成最小修补及离线回归，再核对已有模型配置是否可用；不打印密钥，不自动充值或启动租用服务。
- 用合成用户与隔离数据环境；不操作真实用户计划，不使用真实患者数据。
- 保存可读运行日志、工具行为、实际状态、审批与证据版本；模型回复本身不作为业务成功证据。
- 对失败先归因于理解、上下文、工具、状态或授权边界，不用扩大模型或增加子智能体掩盖问题。
- 本文是验收计划，不表示真实模型或跨日持续运行已完成。

## 当前回放究竟做什么

需要区分三类能力：

1. **查看历史**：聊天中的 `ExecutionTimeline`（执行时间线组件）读取执行事件和轨迹；开发诊断中的 `agent_trace_analysis.py`（运行诊断投影模块）从已保存节点生成脱敏时间线和失败分类。展开不会重做数据库写入。
2. **检查历史输入与状态**：`AgentRunReplay`（运行快照记录）保存请求、状态、工具计划、回复和配置快照。同账号的回放接口返回这些快照。部分上下文被截断，且不是每次模型请求的精确输入，因此不能称为无损复现。快照接口不是开发诊断的脱敏投影，仍可能包含本人原始内容，必须维持鉴权与账号隔离。
3. **重新运行验收**：测试设施在隔离数据库中重建合成用户和旧状态，调用真实业务服务，检查实际写入、记忆有效性、审批范围和结果。它不重放真实账号的写动作，也不是把历史最终回复重新展示一遍。

当前模块级路径：用户输入 → 主流程分发 → 上下文及有效证据 → 领域委派或宿主工具 → 审批与执行检查 → 保存节点/公开事件/快照 → 实时聊天时间线或历史诊断投影。
不能把这些分散来源描述成已经具备统一、完整、可恢复的事件日志。

## 参考 DeepSeek 的下一步可视化设计

官方设计依据：[DeepSeek Harness 架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)。其区分持久会话事件和实时运行事件，以日志投影构建历史及界面，并要求模型可见输入可从日志重建。我们借鉴该原则，不为外观把整个项目改成插件框架。

以下是设计目标，尚未完成实现：

- 一个执行编号关联主任务；每条事件有稳定编号、顺序号、父步骤和子任务关联，避免仅靠名称和时间猜测。
- 统一持久事件包括任务分发、上下文证据选择、子任务启停、每次模型调用的公开元信息、工具申请与结果、审批、写入确认、失效和后续观察。
- 明确区分批准、开始执行、提交成功、结果未知；中断没有成功结果时不可画成成功。
- 同一事件源供应实时更新与历史投影；重连按顺序补齐并去重，而不是维护两套互相不一致的时间线。
- 记录上下文证据编号与版本、工具调用关联、状态变化和失败原因。原始内容仅在账号权限允许的受限诊断中查看，密钥不进入轨迹。
- 模型隐藏推理不是展示目标。显示公开任务说明、实际动作及证据，不能用生成的“思考过程”伪装执行记录。

界面保持用户此前要求的精简：聊天内一行当前动作，展开看主要步骤，再展开完整审计；子智能体嵌套于所属步骤。完整意味着重要动作可追踪，不是默认展示所有内部噪声。

## 现有验收集如何构建

- 固定旅程文件：`algorithm/datasets/fixtures/fitagent_journey_v1.json`。八条人工构造合成案例，包括四条伤情纠正、四条目标替换；同一类别的纠正表达重复，睡眠、疲劳及训练完成情况不同。它是业务回归集，不是丰富语言分布上的盲测集。
- 执行器：`algorithm/evaluation/fitagent_journey_eval.py`。创建隔离合成用户，植入旧记忆，执行纠正、签到、审批、训练记录与结果评估；使用离线模型提供者，不证明真实大模型理解质量。
- 十二个明确检查项：档案纠正、旧记忆失效、旧记忆不再召回、签到重试一次生效、签到不擅自改计划、调整需要审批、审批范围准确、仅一个有效计划、训练记录重试一次生效、评估收集证据、评估完成、经验记忆生成。
- 周边测试另行覆盖权限、依赖失效、审批、轨迹脱敏和路由等；它们不能全部合并宣称为同一份真实模型测试集。
- 语义候选的六十二条验收题属于可选路由模块，不等于上述业务旅程，也不是当前默认分发的必经测试。

下一步真实模型验收应在上述业务脚本之上引入自然对话输入、跨日虚拟时间、拒绝/沉默/计划并发变化、子任务矛盾及中断重连。预先冻结期望动作与禁止动作；先检查实际状态，再检查回复是否准确描述结果。不能只按回复流畅度判定成功。
