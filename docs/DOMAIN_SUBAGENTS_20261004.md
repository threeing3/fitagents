# 领域子智能体：实现与学习说明

本文件记录第一阶段领域子任务；周期复盘现在已增加独立证据分析和方案规划，完整链路与对照边界见 [周期复盘协作说明](REVIEW_COLLABORATION_20261004.md)。普通领域咨询保持下述按需模式。

## 业务边界

训练、饮食和恢复分别是有独立上下文和只读工具循环的子任务。周期复盘调用三个领域；其他任务按既有主次意图选择。记录写入、纠正、风险紧急回复和审批仍在原来的宿主路径。

这不是一次性更换三个提示词：每个子任务可以返回查询动作，得到工具结果后再决定下一步或提交结构化建议。最多三次模型决策，一层委派，不得创建孙任务。当前外层顺序由宿主决定，不宣称自主团队编排。

## 链路

用户输入 → 原有意图与上下文 → 按需委派领域子任务 → 主回复结合有效建议 → 原有回复验证/安全护栏 → 保存执行回放。

训练子任务读取训练记录，饮食子任务读取饮食摘要，恢复子任务读取恢复与症状记录。共同的只读工具是 memory.recall（有效记忆查询）、records.read（领域记录查询）与 constraints.read（当前档案及请求约束查询）。查询没有用户标识或任意参数，宿主闭包固定已认证用户。

子任务只收到当前任务、相关记忆和约束；不传完整聊天历史，不获得数据库会话或写工具。每个子任务独立消息列表，工具结果进入下一次模型输入。

## 记忆互动

沿用 ContextBuilder（上下文构建器）的既有检索与纠正过滤，不建立第二份长期记忆。子任务开始读取当前有效记忆，可以再次查询；提交前重新读取其使用的记忆、约束与记录。如果读到的内容变化，结果失败而不是继续采用旧建议。

记忆引用必须来自实际读取的标识；未知或失效引用会被拒绝。但这只是引用来源核对，不是证明每一句模型结论符合事实。意见、经验和观测不能自动升级为事实。子任务不得自行保存推测或覆盖用户纠正。

## 预算和故障

三个子任务总共最多九次模型调用，共享90秒期限，每个至多三轮。串行运行避免并发操作同一数据库会话；暂不做并行性能承诺。正常模型额度仍由已有提供方检查。

取消向上传播，不转换成成功；失败域不提供可采用建议，其他域可继续完成。返回仅用于当前回复，不缓存子结论供未来自动执行。离线模式事件标为跳过、model_called=false（未调用模型），沿用原回复降级逻辑。

当前限制：证据刷新只是接收时检查，不是跨整个回复生成过程的数据库快照；主回复仍需要既有验证与安全护栏。结果冲突由主回复结合当前约束处理，尚无独立、经过真实模型评测的跨领域冲突裁决器。子任务未连接后台周期任务，未改写原有计划生成和审批模块。

## 前端及回放

公开链路展示委派、开始、记忆读取、只读查询、返回及汇总；不展示内部完整思考、用户原始记忆内容或提供方异常。每个子任务有独立标识，同一子任务生命周期折叠成一条领域记录；完整事件保留在审计展开层。

事件存入父运行日志并关联助手消息。同步与流式聊天都记录；刷新聊天历史仍可回放。完成只表示子任务返回建议，不表示计划已经执行。

## 初次学习的关键问题

1. 为什么不是每个意图都创建子任务？简单写入增加模型跳转只会扩大成本和授权风险。
2. 为什么不把所有记忆发给三个角色？会扩大敏感信息暴露、上下文预算和过时事实干扰。
3. 为什么不同时运行？第一版复用同步数据库会话，先保证隔离和恢复，再独立会话并行。
4. 为什么有三个模型结果也不能宣布成功？必须看真实工具结果和最终业务状态；协议测试不证明模型质量。
5. 为什么角色可以用同一个模型？隔离来自上下文、任务、工具和生命周期，不来自不同模型名称。
