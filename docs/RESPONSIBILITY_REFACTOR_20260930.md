# 长期责任生命周期收敛方案

## 决策

参考用户提供的外部评估，并以本地实现为准：复用 AgentTaskState、AgentTaskEvent、BackgroundTask 和 ReflectionService，不新增责任表，不引入新的任务框架。AgentTaskState 表示长期承诺，BackgroundTask 表示一次执行，事件记录表示审计；记忆不负责调度。

## 分阶段执行

1. 有限期每周复盘：显式创建、用户时区、暂停/恢复/取消/到期、确定性扫描、既有后台 worker 执行、结果展示；不调用模型轮询，不自动改计划。
2. 持久审批与执行恢复：先核定数据库演进范围，再接入已有工具执行器。批准历史不能自动扩大授权。批准必须绑定用户、动作参数、责任版本和有效期。
3. 业务事件与产品交互：训练/打卡事件只更新证据，不自动启动模型；加入聊天创建、界面活动、通知与审批入口。
4. 统一单次执行控制：固定短流程与反馈决策复用执行边界，通过固定案例对比后逐步迁移。

## 第一阶段契约

责任类型为 weekly_training_review，配置保存于 constraints.responsibility，运行进度保存于 progress_json。默认四周，周日 18:00 用户当地时间。内部时间使用 UTC ISO 字符串。到期意味着承诺停止，不声称健身目标已实现。

只允许 read_training_data/create_summary；adjust_plan=ask、delete_record=deny 是明确边界，第一阶段没有执行这两项动作的路径。汇总结果通过认证接口读取，不声称已推送通知。

调度与入队在同一事务内；PostgreSQL 使用责任行锁，SQLite 仅支持单扫描进程。逾期扫描合并到最近一次到期时段，不补跑无上限历史。暂停/取消/到期阻止尚未执行的任务，恢复使旧排队任务失效。每次任务仅尝试一次；进程死亡后 running 任务需人工核对，不盲目重试。

时区夏令时不存在的时间跳过该周；重复小时采用较早一次。复盘窗口按用户当地日历计算，训练时间转成 UTC，且不读取计划触发时间之后的记录。没有证据也只报告证据不足，不能编造训练收益。

## 验收与未完成范围

第一阶段通过隔离数据库验证生命周期、重建会话后的配置、用户隔离、重复扫描、任务失效、时区/夏令时及真实后台入口。第一阶段结束时审批还是内存草稿，第二阶段已替换为持久化审批，见下节。没有真实用户数据、线上运行或推送效果证据。

## 第二阶段实施（用户已允许修改模型及迁移源文件）

审批服务已改为读取 pending_approvals，而非请求内存字典。015_pending_approvals 是新增表迁移，未对现有数据库执行。回滚源码保留审批审计表，不删除数据。

批准只覆盖一个用户、工具、完整参数、后台任务、责任配置版本、计划内容快照和有效期。去掉“批准三次即自动授权”。审批数量超过上限时拒绝新增，不默默否决旧请求。拒绝/过期取消待执行任务；批准将同一任务从 waiting_approval 转成 queued。

首个审批动作只支持指定日期减少1–3组，且每个动作必须保留至少1组。其他日期、次数、动作类型、饮食信息均保持不变。待执行草案绑定完整基线，期间计划或责任变化会使草案失效。审批默认24小时有效，不授予未来调整权限。工具执行、计划保存、审批消耗和任务完成共用事务；失败回滚，不重试。

该动作真实经过 ToolRegistry.execute_awaiting_approval，生成 AgentRun 和责任事件。现有普通聊天工具流不变。它是一个接入业务的审批切片，不是通用跨任意工具断点恢复；没有自动审批、任意增加强度或整周重生成入口。

## 接口与操作顺序

- POST /v1/responsibilities/weekly-review：结构化创建；source_instruction、weeks、weekday、hour、minute。时区来自已认证用户。
- GET /v1/responsibilities：查看配置、下一次唤醒和复盘结果。
- POST /v1/responsibilities/{id}/lifecycle：pause/resume/cancel。
- POST /v1/responsibilities/{id}/plan-proposal：plan_id、day_date、reduce_by、reason；创建草案和同一待审批后台任务，不修改计划。
- GET /v1/approvals/pending：读取跨会话审批。
- POST /v1/approvals/decide：approval_id、action=approve/deny、reason；批准后由已有后台 worker 执行。

启动实际服务前需要审阅并单独授权在目标数据库应用015迁移。不要直接运行 worker 连接未审阅的旧业务数据库。当前测试仅在新建隔离数据库中创建模型，不验证生产 PostgreSQL 迁移执行、并发或故障恢复。

有时间戳的训练/动作/决策采用连续七天窗口（含起点、不含截止点），避免漏掉周日晚间记录。只有日期的饮食/恢复记录沿用日历周口径，可能在跨截止日记录中重叠；目前不能声称精确到小时的全域证据截断。

专项测试78通过；完整后端1016通过、2跳过，覆盖率77.27%。修改的16个Python文件静态检查与格式检查均通过，项目类型检查通过，接口定义生成成功。测试使用合成数据和隔离数据库，验证的是实际服务、队列、审批及工具执行代码，不包含真实模型推理、生产PostgreSQL迁移或并发验收。执行日志位于logs/responsibility_refactor_20260930.md。

## 第三阶段：聊天与复盘草案

已接入普通及流式聊天的同一受限命令实现，复用现有请求幂等记录。创建要求完整匹配明确指令，不依赖模型猜测日期或授权。示例：

- 创建4周每周日18:00训练复盘，调整先问我
- 查看训练复盘责任
- 暂停训练复盘 责任编号（恢复、取消同理）
- 查看待审批调整
- 批准调整 审批编号（拒绝同理）

当前是有限模板入口，不是任意中文表达理解；不完整的创建请求返回明确格式，询问、否定、举例不作为创建指令执行。聊天回复显示责任编号、审批编号、调整日期、范围、理由及有效期。批准回复只确认排队，不把批准说成计划修改成功。

周复盘使用可追溯的结构化恢复证据：至少3个已结束日期的有效疲劳评分，均值达到7且窗口无症状记录，才可提出下一次训练各动作减1组的草案。这是合成业务演示规则，不是临床阈值，不证明训练效果。当天只有日期的恢复记录不用于提案；延迟超过24小时的复盘仅保留总结，不根据过期证据提案。计划必须唯一、有效且包含未来7天内明确日期；调整不能超出责任期限。不做任意增加强度或改变动作类型。

没有证据、存在症状、多个计划、未解决的旧调整或不适用的动作组数时，记录不提案原因。草案校验失败使用局部事务回滚，不留下孤立任务、不丢弃复盘。草案保留评分来源；等待审批期间计划不变，批准后仍复核计划快照与责任状态，再由已有后台执行器执行。

第三阶段结束时尚未新增前端活动页或主动通知，第四阶段已接入长期跟踪页面，见下节。后台复盘仍需运行现有工作进程；当前并未启动连接旧业务库的进程。

第三阶段最终完整回归1034通过、2跳过，覆盖率77.41%；19个修改的Python文件静态检查及格式检查通过，项目类型检查通过。专项回放、完整回归、失败修复与数据模拟说明见logs/experiments/20260930_responsibility_chat_review.md。测试覆盖实际聊天服务、责任服务、复盘、持久审批和后台计划工具；不把演示策略或模拟时间回放说成真实用户效果。

## 第四阶段：可交互页面与执行结果

导航新增长期跟踪页面，提供周数、复盘日、账户当地时间的结构化创建；查看责任、下一次触发、到期和最近复盘及来源；暂停、恢复和确认取消；查看草案日期、范围、依据、有效期并单次批准/拒绝。历史卡片在审批后仍保留，严格区分已批准待执行、已执行且校验通过、已拒绝、过期、计划/责任变化失效、失败和结果未知。

新增GET /v1/approvals/history?limit=30，按认证用户读取审批和对应后台任务，输出审批状态、任务状态、执行结果、错误与有效期。不把任务completed或用户批准当作计划写入成功；界面只有审批executed、任务completed、结果adjusted且verified=true时显示计划校验通过。GET /v1/approvals/pending补充有效期。

每15秒仅在页面可见且没有写入时刷新读取状态，不触发模型或任务执行。写操作禁止重复点击，在发出请求前把未确认标记按用户写入当前浏览器会话存储；断线或重载不自动重发。用户需要刷新核对记录后人工解除锁。结构化创建接口尚无服务端幂等键，因此不宣称任意人工重试下恰好一次。

独立入口/?demo=responsibilities无需登录，使用内存合成数据，明确标注不连接业务数据库，后台为界面模拟。可演示查看证据、批准一次、手动推进模拟后台及执行状态变化；重载会重置演示，不影响真实数据。演示不等于真实后台部署。真实服务、队列、审批和写后验证另由隔离数据库测试覆盖。

本阶段最终后端1036通过、2跳过，覆盖率77.42%；前端组件17通过、浏览器6通过，类型检查和构建通过。测试记录和桌面/手机截图见logs/experiments/20260930_responsibility_frontend.md。演示地址http://127.0.0.1:4173/?demo=responsibilities，仅需前端预览进程，无需启动API或工作进程。仍未迁移现有数据库、启动真实工作进程、上线通知或使用真实用户数据。

## 第五阶段：持久执行事件和共享展示

新增execution_event（公共执行事件，描述可核对的决策和执行边界），字段包括名称、来源、状态、记录时间、摘要和参数/证据。来源区分执行控制、规则、用户决定、工具及模型摘要；当前责任链路实际使用规则，不生成虚构模型思考。事件持久化复用审批上下文、任务进度和运行节点，不新增数据库表。

复盘保存证据窗口和规则依据；审批保存等待、批准/拒绝和过期；后台执行保存责任/计划复核、工具启动、写后校验和完成。写入失败时整个事务回滚，随后保存回滚失败事件，不把回滚前的校验成功当作已提交结果。工具调用耗时来自已有执行器；没有杜撰模型耗时。进程崩溃且事务未提交的中间步骤不会被单独保留，不宣称跨任意故障完整实时追踪。

新责任聊天命令流返回已保存的公共事件，消息历史通过运行记录的消息关联恢复事件，再补入同用户审批的最新执行记录。重新加载会话后，可以从批准消息看到后台后来完成的校验，不会跨用户读取。短命令事件在事务保存后发送，是可回放的过程，而非模型内部思维或每一步实时事务流。

聊天回答与长期跟踪页复用ExecutionTimeline（执行时间线组件，展示同一事件结构），默认折叠，展开可看来源、状态、记录时间和参数依据。普通旧聊天保留原过程卡片，但按服务端状态显示，失败不再打勾、缺失状态显示未确认、未知工具不被分组丢弃；不是所有旧工具链都已迁移到新事件格式。

合成演示在每条事件摘要标注界面模拟。打开演示后批准一次并推进模拟后台，可展开历史中的执行过程查看规则→授权→复核→工具→验证；不要把模拟记录当作生产执行证据。验证过程见logs/experiments/20260930_execution_journal.md。

本阶段最终后端1037通过、2跳过，覆盖率77.52%；前端组件19通过、浏览器8通过，静态、格式、类型及构建检查通过。仍未应用数据库迁移、启动真实业务任务或进行真实模型网络联调。
